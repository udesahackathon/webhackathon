## Core

### Module refs por IS-A (`8fac510`)

`_resolve_single_ref` en `module_coordinator.py` comparaba con identidad exacta de clase:

```python
# antes
return cls is spec if is_class_ref else spec_structural_compliance(cls, spec)

# ahora
if is_class_ref:
    return isinstance(cls, type) and issubclass(cls, spec)
return spec_structural_compliance(cls, spec)
```

Con identidad exacta, un deployment que sustituía el provider por una subclase (para agregarle
puertos) dejaba la ref en `None` **en silencio**: sin error al cablear, y `AttributeError` recién
en el primer uso. Esto no es un detalle aislado, es lo que habilita el patrón nuevo de
"subclasear el `ControlCoordinator` para declarar puertos extra" que documenta el refactor de
control.

### `build_native` leído del config correcto (`7a0a970`)

`native_module.py` leía `global_config.build_native` en vez de `self.config.g.build_native`, así
que el flag no respetaba los overrides por módulo.

## Mensajes: se fue `plum-dispatch` (`016405b`)

Los constructores multi-dispatch de `msgs/` estaban hechos con `@dispatch` de `plum`. Se
reemplazaron por `@typing.overload` más un `__init__(*args, **kwargs)` que discrimina a mano.

```python
# antes
@dispatch
def __init__(self, pose_tuple: tuple[VectorConvertable, QuaternionConvertable]) -> None: ...

# ahora
@overload
def __init__(self, value: PoseConvertable | Pose, /) -> None: ...

def __init__(self, *args: Any, **kwargs: Any) -> None:
    """Pose(), Pose(x,y,z), Pose(x,y,z,qx,qy,qz,qw), Pose(position),
    Pose(position, orientation), Pose((position, orientation)), Pose({...})"""
```

Es un cambio de performance (plum resuelve tipos en runtime en cada construcción, y estos tipos
se construyen en loops de control). La API pública se mantiene: las mismas formas de llamada
siguen funcionando. Tocó `Pose`, `Quaternion`, `Twist`, `JointState`, `Joy`, los `*Stamped` y los
`*WithCovariance`, y sumó `test_msg_construction.py` (785 líneas) que fija todas las formas.

Ojo: aparecieron helpers de desambiguación como `_is_position_orientation_pair`, que distinguen
"par (posición, orientación)" de "posición 2D" mirando si los elementos son numéricos. Es más
frágil que el dispatch por tipos, pero está cubierto por tests.

`Wrench` y `WrenchStamped` sumaron encode/decode LCM propios (`7a5a844`); antes no serializaban.

## Control: el refactor grande (`6580b67`, `1bc1e97`, `cee5cdb`)

Es el cambio más profundo del rango. Reescribe cómo el `ControlCoordinator` descubre tareas,
rutea mensajes y publica estado. Ver `dimos/control/README.md`, que quedó rehecho.

### Task cards

Cada tarea publica un manifiesto en `dimos/control/tasks/<task>/_registry.py`. `tasks/registry.py`
los descubre **sin importar la tarea**, así que las dependencias pesadas (Pinocchio, ONNX
Runtime) se cargan recién cuando la tarea se instancia.

```python
TASK_FACTORIES = {"servo": "dimos.control.tasks.servo_task.servo_task:create_task"}
TASK_CONSUMES  = {"servo": {"joint_command": ("on_joint_command", "claim_overlap")}}
TASK_EXPOSES   = {"trajectory": ["execute", "cancel", "get_state"]}
```

`TASK_EXPOSES` define qué puede llamar `task_invoke`, y la firma del método **es** el schema de
argumentos: `task_invoke` bindea kwargs contra ella y un typo revienta del lado del caller.

### Reglas de ruteo

| Regla | Entrega cuando | La usa |
|---|---|---|
| `claim_overlap` | el mensaje nombra un joint que la tarea tiene tomado | `joint_command` |
| `broadcast` | siempre, a todas las tareas del puerto | `teleop_buttons`, `gripper_command` |
| `direct` | siempre, pero el puerto es para una sola tarea (una segunda loguea warning) | `path`, `speed` |
| `by_task_name` | `msg.frame_id == task.name` | comandos cartesianos y de twist EEF |

`by_task_name` usa `frame_id` como dirección y no como frame de coordenadas. El propio README lo
marca como legacy y pide no agregar bindings nuevos.

### I/O por deployment

Un deployment que necesita puertos extra **subclasea** el coordinator y los anota:

```python
class _Go2Coordinator(PathFollowingCoordinator):
    go2_joints: Out[JointState]

blueprint = _Go2Coordinator.blueprint(
    instance_name="ControlCoordinator",   # los clientes RPC lo buscan por nombre de clase
    publish_robot_joint_states=True,
)
```

Esto es exactamente lo que arregla `8fac510`. Los puertos de las cards se validan contra la
instancia viva al arrancar (no contra el registry, que no ve las subclases), y si falta un puerto
falla `add_task()` con la anotación que hay que agregar, antes de registrar ninguna ruta.

`TaskConfig.stream_bind` permite remapear una entrada por instancia, así dos tareas del mismo
tipo leen puertos distintos (remapping al estilo ROS).

### Dos vistas del joint state

| Vista | Stream | Lleva | La habilita |
|---|---|---|---|
| Agregada | `coordinator_joint_state` | todos los joints, `frame_id="coordinator"` | `publish_joint_state` (default on) |
| Por robot | `{hardware_id}_joints` | un robot, `frame_id=hardware_id` | `publish_robot_joint_states` + anotación `Out[JointState]` |

Ambas son permanentes y salen de la misma lectura por tick, con nombres canónicos
`{hardware_id}/{joint}`. Esa es la vista de *control*. Los módulos de conexión (`GO2Connection`,
`G1WholeBodyConnection`) publican la vista de *dispositivo*: estado crudo, al rate del device.

La regla para elegir: por lo que es el consumidor, no por cuántos robots hay. Consumidores que
capturan lo que haya (`CollectionRecorder`, `WorldBeliefRecorder`, `ManipulationModule`) leen la
agregada; los que hablan de un robot puntual leen la del robot.

## Manipulación

### Frontera path → trayectoria (`d6cf473`)

El cambio conceptual: un planner de joint space devuelve un **path geométrico sin tiempo**. Antes
de aceptar un `GeneratedPlan`, ahora un backend de parametrización (elegido al arrancar) lo
convierte en un `JointTrajectory` con tiempos, y DimOS valida orden de joints, dimensiones,
valores finitos, tiempo estrictamente creciente y preservación de start y goal.

| Backend | Cuándo es default | Qué hace |
|---|---|---|
| `simple_trapezoid` | con `DrakeWorld` | trapezoidal por segmentos (el comportamiento viejo) |
| `roboplan_toppra` | con `RoboPlanWorld` | TOPP-RA, timing continuo sobre todo el path |

Reglas importantes:

- **No hay fallback.** Si el parametrizador elegido falla, no se prueba otro y no queda plan
  ejecutable cacheado.
- Si el planner ya devuelve timestamps y velocidades, se saltea la parametrización y se respeta
  su timing, pero se valida igual.
- `roboplan_toppra` solo corre con `world_backend="roboplan"`; con otro world falla al arrancar.
- El slider "Next plan speed" de Viser (0.05 a 1.0) multiplica las escalas de velocidad y
  aceleración **del próximo plan**, no del plan ya aceptado.
- Cada joint movible necesita límite de velocidad finito y positivo en el URDF. Si no hay
  aceleración autorada, se inserta un fallback global de `2.0 rad/s²`, marcado como temporal.

La frontera quedó expuesta como `TrajectoryParametrizerSpec`, al lado de `PlannerSpec` y
`WorldSpec`. `manipulation_module.py` adelgazó fuerte (+82/-201) porque le sacaron esa lógica.
De paso desapareció el `CONTEXT.md` de la raíz del repo.

### RoboPlan como planner propio (`4c227a5`, `2b6ff61`)

`roboplan_planner.py` (681 líneas nuevas) saca la lógica de planificación de
`roboplan_world.py` (que perdió 565 líneas). Suma shortcutting y split planner, y
`roboplan_config.py` separa la config. El fix `2b6ff61` hace que el planner use el estado del
robot **capturado** al inicio de la planificación en vez de releerlo, que es el bug clásico de
planificar contra un estado que se movió mientras tanto.

### GraspGenX (`54ea8d1`)

Provider nuevo de propuestas de grasp, adaptando el modelo de NVlabs. Suma
`GraspCandidate` / `GraspCandidateArray` a `manipulation_msgs`, y el blueprint
`grasp-gen-x-module`. El adapter (`grasp_gen_x.py`) es "import-safe": el runtime pesado vive
aparte en `grasp_gen_x_runtime.py` y se carga tarde. Modelo y revision están pineados
(`adithyamurali/GraspGenXModel`).

## Teleop: manos de Quest (`eeae9a2`)

Control por hand tracking, sin controllers. Pinch pulgar + índice para enganchar la mano y mover
el brazo con la muñeca, pinch de nuevo para soltar. Pinch pulgar + mayor cierra el gripper,
soltar lo abre. Requiere hand tracking habilitado en el browser del Quest.

Blueprint: `teleop-quest-hand-xarm7`. Módulo: `HandTeleopModule` en `quest_extensions.py`.
